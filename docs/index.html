kurwadb распределённое множество · elixir / beam

Ключ сам себе значение

Хранит ключи и ничего больше: ни значений, ни сканов, ни запросов, ни лидера. Одно ограничение, которое упрощает всё остальное.

{key, lamport, node, alive?, wall}

Вот и вся запись. Места для значения в ней нет — поэтому слияние двух реплик сводится к сравнению двух чисел.

Репозиторий ADR Архитектура
API

Четыре операции, и всё

Kurwa.add("order:1029")      #=> :ok
Kurwa.member?("order:1029")  #=> true
Kurwa.delete("order:1029")   #=> :ok
Kurwa.count()                   #=> {:ok, %{approximate: 1, ...}}

Kurwa.add("seen:event:88", ttl: :timer.minutes(10))

Плюс именованные множества и алгебра над ними: member_any?(["blacklist", "greylist"], key).

Почему

Цепочка следствий

  1. У ключа нет содержимого.
  2. Две конкурентные записи не могут разойтись ни в чём, кроме факта существования.
  3. Слияние реплик = сравнение {lamport, node}. Полный порядок.
  4. Значит, не нужны vector clocks, siblings и merge-функции в приложении.
  5. И не нужен лидер: любая нода обслуживает любой ключ.
Что даёт

Шесть свойств, за которые всё это затевалось

Нет лидера
Нечего выбирать, нет паузы на failover. Потеря ноды забирает ёмкость, а не доступность.
Самолечение
Упавшая нода не выпадает из кольца: пропущенные записи копятся и доезжают сами, когда она вернётся. Без оператора.
Ошибка ≠ отсутствие
Недостижимый кворум — это 503, никогда не false. Именно здесь врёт дедупликация на кэше.
361 нс
Локальная проверка принадлежности — один :ets.lookup в процессе вызывающего, без переключения контекста.
Монтируется
Ядро не знает про протоколы, поэтому БД отдаётся и по 9P: ls, cat, stat вместо админских ручек.
Ключи истекают
Координатор превращает TTL в абсолютный момент один раз, поэтому все реплики приходят к одному вердикту сами, ничем не обмениваясь — истёкшему ключу не нужно надгробие, чтобы остаться удалённым.
Union бесплатно
Объединение именованных множеств считается на чтении и ничего не копирует. Это union mount из Plan 9, только для множеств.
Замеры

Скорость — часть контракта

Релиз, который медленнее предыдущего, считается сломанным. Регрессия — это баг релиза, а не новая точка отсчёта.

Поэтому каждая цифра ниже получена скриптом из bench/ в репозитории, и у каждой версии своя колонка в PERFORMANCE.md.

Операция0.2.0
Локальная проверка принадлежности361 нс
Кворум трёх нод, один клиент~47 мкс
Кворум трёх нод, 64 клиента56k зап/с · 58k чт/с
GET /k/:key по HTTP, keep-alive126k зап/с
POST /batch, 100 ключей в запросе408k ключей/с
Память на ключ128 Б · 152 Б

Apple M4, 10 ядер; все три ноды делят один процессор, n=3 r=2 w=2. 128 байт — при 13-байтном ключе, 152 — при 36-байтном. Переиспользование соединения даёт ~4×: без него те же запросы дают 32.5k/с, и это измеряет TCP, а не базу.

Как устроено

Схемы

9P

База данных как файловая система

stat — это и есть проверка принадлежности, create — добавление, remove — удаление. Не метафора, а та же модель данных.

9p -a localhost:564 ls /
ctl  stats  ring  keys  b64  sets

9p -a localhost:564 read ring
member kurwa1@10.0.0.1 up
member kurwa2@10.0.0.2 up
member kurwa3@10.0.0.3 down

echo compact | 9p -a localhost:564 write ctl

Никакого SDK и вендорского CLI. Каталоги ключей намеренно нелистируемы — сканов в базе нет, а пустой листинг был бы ложью.

Границы

Когда не брать

  • Одна нода. Redis лучше по всем статьям: проще, быстрее, десять лет в проде, экосистема.
  • Допустимы ложные срабатывания и не нужны удаления. Bloom-фильтр съест ~1,2 байта на ключ против наших 120.
  • Нужны сканы, листинги, запросы. Их нет намеренно, и это не изменится.
  • Ключи не влезают в RAM. ~11 ГБ на 100 млн ключей; дискового движка пока нет.
  • Ноль часов в проде. Один автор, нет клиентских библиотек, нет TLS между нодами.
